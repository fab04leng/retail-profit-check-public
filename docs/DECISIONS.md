## Phase 2 — Data layer

- **Dates:** day-first (DD/MM/YYYY) is the default, as in Malaysia. A date column is read month-first only if one of its values has a middle part above 12 and none has a first part above 12. Two-digit years mean 20YY. Excel serial numbers and Malay/English month names (e.g. "5 Ogos 2026", "31 Dis 2025") and `2026年1月12日` are accepted.
- **Numbers:** `RM`/`MYR` prefixes, thousands commas, `(12.00)` and `12.00-` negatives, full-width digits and European `1.234,56` are accepted. `1,234` is always one thousand two hundred and thirty-four.
- **Sales total:** if a Total column is mapped, it is taken as the net line amount after discount. Otherwise total = qty × unit price − discount. A `10%` discount is converted to RM.
- **Refund signs:** a line with positive quantity and negative amount (or the reverse) is treated as a refund (both negative) and a warning is shown, because POS exports differ.
- **Sales without SKU:** the product name becomes the key; at least one of SKU/name is required. Same for the product list.
- **Duplicate SKUs in the product list** (e.g. one row per outlet): quantities are added, unit cost becomes the quantity-weighted average, and a warning lists the rows.
- **Negative stock on hand** is kept with a warning and counted as zero in stock value. **Negative unit cost** rejects the row.
- **Row numbers** are the row numbers the user sees in Excel (header row included, blank lines kept), so evidence can be found in the original file.
- **Header row detection:** the first of the top 15 rows that matches the most known column names, so report titles above the header are skipped.
- **Remembered mappings:** stored per file layout (hash of normalised headers) in `localStorage`, wrapped in try/catch. Only the mapping (column numbers) is stored — never file contents.
- **Text from files** is trimmed, stripped of control characters and capped at 200 characters; it is only ever rendered as text.
- **Demo data:** generated in the browser from a fixed seed (no large file download needed); the same generator writes `demo/data/*.csv` for people who want to try the upload flow. Supplier and shop names are coined words chosen to avoid matching real businesses; product names are generic descriptions without brands.
- **Answer key timing:** the planted cash-crunch week depends on the cash-flow method, so `demo/ANSWER_KEY.md` is generated (from the generator's own planted list) together with the analyses in Phase 3.

## Phase 3 — Analyses

- **Unit cost** comes from the product list (current cost) and is applied to all sales in the period. No FIFO/weighted history. Simple and transparent; noted as a limitation.
- **Category** for profit comes from the product list when the SKU is there (master data), else from the sales file.
- **Below cost** is judged on the product's average net selling price across the period (not single lines), so one promotional sale does not trigger it. The RM figure is cost of goods sold − revenue on those rows.
- **Low margin** excludes below-cost products (they already have a stronger finding). Its RM figure ("gap to target") is shown but never added into headline totals.
- **Stock age** counts from the last sale (refunds ignored). Never-sold items age from their last received date, or from the first sales date. Dead stock = more than 90 days, matching the 91–180 bucket boundary.
- **Invoice copies:** lines with the same supplier + normalised invoice number form one invoice. Copies on other dates, or all lines repeated on the same date, are SUP-01 findings; for payments and cash flow the invoice counts once (first copy).
- **SUP-02** compares invoice totals exact to the sen, within the window, different invoice numbers.
- **SUP-03** compares each invoice line with the previous line for the same supplier + SKU (or description), using one copy of each invoice. Exactly 5% is not "more than 5%". The RM figure is the extra paid on that line versus the previous price.
- **Payment matching:** reference contains the invoice number (short numbers must match exactly; a number is not matched inside a longer number). Otherwise exact amount, same supplier, on/after invoice date, within 120 days, to an invoice not yet fully paid. Negative payments (supplier refunds) reduce the paid amount if matched, and are never flagged as unmatched.
- **Without a payments file**, payment rules do not run and the cash-flow outlook treats invoices due on/after the forecast start as unpaid (earlier ones assumed paid).
- **Cash-flow method:** least-squares line through the last 8 complete Monday–Sunday weeks, extended 8 weeks, floored at zero. Cash in = forecast sales (retail is mostly cash/card). Out = unpaid invoices by due date (overdue → week 1), fixed monthly costs on their day of the month, and (optional, default on) estimated restocking = forecast sales × historical cost ratio, paid `round(terms/7)` weeks later. Possible duplicate invoices that are unpaid stay in the outlook (prudent); the accountant can mark them.
- **Demo calibration:** the demo opening balance (RM 20,000) and fixed costs were chosen so exactly one week (16–22 Nov 2026) dips below zero, driven by the planted year-end orders. This calibration is stated in the answer key.

## Phase 4 — UI

- **Engine in a Web Worker:** files are read, normalised and analysed in a worker; the page asks it for source rows on demand when someone opens the evidence for a finding (max 200 rows shown, all row numbers listed). If the worker cannot start within 4 s (e.g. `file://`), the same engine runs on the page.
- **Hash navigation** (`#/profit`) only ever carries page names, a rule id or a headline key — never file contents.
- **Persisted in localStorage** (all wrapped in try/catch): language, review-mode toggle, thresholds, cash-flow inputs (separately for demo and own files), column mappings per layout, and review statuses/notes per dataset (demo, or a hash of the files' layouts, row counts and names). "Clear data and remembered settings" removes all of it.
- **Review statuses:** Confirmed / Not an issue / Needs info, with a note. Typing a note on an unreviewed finding marks it "Needs info". The report counts confirmed findings (and their RM total, excluding estimates and margin gaps) separately from unreviewed ones.
- **Colours:** single blue series for magnitude charts; the reserved "critical" red only for below-minimum cash weeks and always with an icon and a text label. Light theme only (a printed/business tool); system fonts only (no web-font download).
- **Malay translation** was produced in the same pass as Chinese (stretch goal 1) because it costs little extra; all three dictionaries are checked for identical keys and placeholders by `tests/unit/i18n.test.ts`.
- **Outlet comparison page** (stretch goal 2) was added with the core UI because the profit analysis already groups by outlet.
- **Excel export of findings** (stretch goal 5) uses `write-excel-file`, loaded only when clicked; text cells are written as strings (never formulas) and guarded against formula injection; CSV export uses the same guard.
- **Demo shop name** stays in English in all languages (it is data, not UI text).

## Marketing agent (n8n) — `marketing-agent/`

Worked unattended on branch `marketing-agent`; decisions logged here instead of asking.

### Part 1 — foundations
- **Source of truth is code, not hand-edited JSON.** Workflows are generated by `marketing-agent/src/build.mjs` from `src/workflows/*.mjs`. Logic that runs inside n8n Code nodes lives in `src/lib/*.cjs` and is inlined at build time, so it is unit-tested once (`node --test`) and identical in every workflow (for example, the brand-rule check runs in the generator, publisher, lead inbox and reply sender).
- **Target n8n version:** current stable **n8n 2.46.6** (npm `latest`, Nov 2026). Node type versions were chosen to exist in **both 2.46.6 and 1.123.92** (last 1.x), so older self-hosted installs can import the workflows too. `scripts/validate.mjs` checks both, using n8n's own published node descriptions (`n8n-nodes-base/dist/types/nodes.json`) and `n8n-workflow`'s `NodeHelpers` for parameter checks.
- **Settings live in a "config" tab of the Google Sheet**, not in n8n. Only the sheet ID is typed into each workflow (a "Settings" node). Reasons: one place to edit for five workflows; n8n Variables (`$vars`) are not on every plan; a beginner can flip `DRY_RUN` without opening n8n. Secrets never go in the sheet: they stay in n8n credentials.
- **Safe defaults:** `DRY_RUN = TRUE` and `USE_FAKE_LLM = TRUE`. A fresh import posts nothing, sends nothing and needs no LLM key. Fake LLM text is tagged `[FAKE LLM TEST]`, and the publisher and reply sender refuse such text when `DRY_RUN` is FALSE.
- **Brand rules are enforced in code as well as in the prompt.** BLOCK rules (fraud/accusation words, "replaces your accountant", tax advice incl. LHDN/e-invoicing, guarantees, calling the product AI, audit claims, email addresses, placeholders, phone numbers other than ours) stop a post or reply even if a human approved it, because the check re-runs on the sheet text at send time. CHECK rules (RM figures or percentages without a demo-data label, pressure words, more than 4 hashtags, too long, company-name suffixes) are warnings only. Honest disclaimers ("not tax advice", "we can't guarantee") are allowed by a negation guard; Chinese negators must sit right before the match because 不 is common.
- **Demo-data label check runs on the post body only**, because the call to action itself says "fictional sample shop" and would otherwise count as a label. The real pilot fee (RM300, RM300–RM800) is excluded from the RM-figure warning.
- **The LLM never writes links, phone numbers or prices.** The call to action (wa.me link with `?text=PROFIT|STOCK|INVOICE`) is added by code, which also makes pitch attribution deterministic.
- **Pitch attribution:** the code in the WhatsApp link (or `m.me/?ref=CODE`), `ref: CODE` in text, or the code typed in upper case. Lower-case words ("my stock") do not count.
- **Lead IDs are an FNV-1a hash** of source + contact ID, so the ID does not expose a phone number.
- **Dates:** written as `YYYY-MM-DD HH:mm` Malaysia time with `cellFormat: RAW`; the reader also accepts day-first `DD/MM/YYYY` (Malaysian sheet locale), ISO strings and Sheets serial numbers. SETUP asks for the sheet locale to be Malaysia. A sheet set to the US locale would show month-first dates that the reader would misread; this is documented, not detected.
- **Fake test data** uses `6010000000x` numbers and `PSID_TEST_*` IDs. The validator rejects any other Malaysian phone number or non-`example.com` email anywhere in `marketing-agent/`.

### Part 2 — Workflow 1, content generator
- **Schedule: Friday 10:00 Malaysia time, writes next week's drafts** (`WEEK_OFFSET = 1`), so there is a weekend to approve. Workflow time zone is `Asia/Kuala_Lumpur`.
- **"Rotating 3 pitches" = every pitch every week, in a rotating order.** Three slots (default Mon/Wed/Fri 20:30), one pitch each, order shifted by ISO week number. Each pitch gets each weekday in turn and appears equally often, which keeps the per-variant comparison in the weekly report fair. Each slot is drafted in EN and casual Malaysian Chinese (6 drafts a week). BM can be added with `LANGUAGES = en,zh,ms`.
- **LLM node = HTTP Request to `{LLM_BASE_URL}/chat/completions`** with a Header Auth credential, not n8n's LangChain OpenAI node. It works with any OpenAI-compatible provider (OpenAI, OpenRouter, DeepSeek, Groq, a local Ollama), has a simple, version-stable parameter shape, and allows JSON mode (`LLM_JSON_MODE`, switch off if a provider rejects `response_format`). Retries 3 times.
- **Brand rules and brief are fetched by URL** (a secret GitHub Gist "Raw" link works). This works the same on n8n Cloud, which has no file system access. If the download fails, the fake-LLM test still runs; the real LLM is never called without both files.
- **A second run for the same week stops with a clear error** instead of duplicating or overwriting drafts (overwriting could undo approvals).
- **One text cell = exactly what gets published** (body + call to action + hashtags), so what you approve is what posts. The same text is used for Facebook and Instagram: the wa.me link is clickable on Facebook, and on Instagram people can read the number and the code.
- **Runtime test in real n8n.** `scripts/runtime-test.mjs` imports the workflows into a temporary n8n 2.46.6 (CLI, SQLite) with external nodes swapped for Code nodes of the same name, runs them, and reads results from n8n's execution database. Found during this: **n8n refuses to start a workflow if any node references a credential you cannot use, even on a branch that will not run** (for example "Call LLM" in fake mode). SETUP therefore asks for every credential to be created before the first test (a dummy LLM key is fine while `USE_FAKE_LLM = TRUE`). n8n 2.x needs Node.js 24+; `n8n execute` often reports "No active execution found" for fast runs, so results are read from the database instead.

### Part 3 — Workflow 2, publisher
- **"When a row is marked approved" is implemented as an hourly check (07:00–23:00 MYT), not a Google Sheets Trigger.** A polling Sheets Trigger fires on any edit (including the workflows' own writes), needs a second Google credential type and the Drive API, and cannot wait for `scheduled_for`. The hourly schedule posts approved rows at their scheduled hour; the default post time moved to 21:00 so it lines up with the hourly run.
- **n8n Cloud execution budget:** every scheduled run counts as an execution on n8n Cloud. Hourly 07:00–23:00 is about 520 executions a month. SETUP explains how to slow it down; self-hosted n8n has no limit.
- **One post per run**, oldest scheduled first. It keeps Meta rate limits and mistakes small (a wrongly approved batch cannot all go out at once).
- **Locking:** the row is set to `publishing` before anything is sent, and the final status is `posted`, `posted (dry run)` or `error`. A failed or half-done post (for example Facebook OK, Instagram failed) is **never retried automatically**: it becomes `error` with the Facebook ID kept and "Partly posted – check the Page", so nothing is posted twice.
- **Brand rules are re-checked at publish time** on the text as it is in the sheet (it may have been edited after drafting). BLOCK → `blocked`; the human edits and approves again.
- **Instagram requires an image** (`image_url`, public JPEG link); without one the row becomes `needs image` before anything is posted, so Facebook does not go out alone by surprise. Facebook posts with an image use `/{page}/photos`, without one `/{page}/feed`.
- **Meta Graph API via HTTP Request + n8n's "Facebook Graph API" credential** (Page access token as `access_token`), not the Facebook Graph API node, so request bodies are plain JSON and the API version is a config value (`GRAPH_API_VERSION`, default `v25.0`, the newest version listed in n8n 2.46.6's own Facebook node). Instagram: create container → wait 20 s → `media_publish`. **Unsure:** large images can take longer than 20 s to process; if `media_publish` reports the media is not ready, the row shows `error` and can be re-approved. A status-polling loop was not added, to keep the workflow simple.
- **Runtime-tested in n8n 2.46.6** with the real HTTP Request nodes pointed at a local mock Graph API (request paths and bodies asserted): dry run, live photo + Instagram, Instagram failure, text-only post, missing config.

### Part 4 — Workflow 3, lead inbox (+ 3b reply sender)
- **Inbound only, by construction.** The inbox starts only from Meta webhooks (WhatsApp Trigger, Facebook Trigger on the Page object), so a lead row exists only because that person wrote to us. There is no node anywhere that sends WhatsApp templates, broadcasts, or messages to a number that is not already a lead who wrote in.
- **Sending approved replies is a separate workflow (3b)**, because n8n's webhook triggers and the reply schedule need different starting points and the same sheet ID; two small workflows are easier to test and to switch off independently. 3b runs every 20 minutes, 08:00–23:40 (about 1,450 executions a month on n8n Cloud; adjust in SETUP).
- **24-hour customer-service window enforced in code** (`REPLY_WINDOW_HOURS`, default 23 h for safety, hard maximum 24 h). After that the row becomes `window closed` and nothing is sent; the person has to write again (no template re-engagement, which would be outreach).
- **Opt-outs without the LLM:** "STOP", "unsubscribe", "berhenti", "停止/取消", "don't message me", "不要再发" and similar → `intent = not_interested`, `do_not_contact = yes`, and a fixed polite acknowledgement for approval. 3b allows exactly that acknowledgement and then **removes the number, name and message from the sheet** (the row stays for the weekly counts). Any other reply to a `do_not_contact` contact is blocked until a human clears the flag. If an opted-out person writes again, the draft is flagged so a human decides.
- **First reply to a new contact gets a short privacy line** (we use your number only to reply; reply STOP to stop and delete), plus `PRIVACY_NOTICE_URL` if set. This is a practical PDPA notice, not legal advice.
- **Intent set:** exactly question / wants_demo / not_interested. Anything else from the LLM becomes `question` with a CHECK flag. Non-text messages (photos, voice notes) are saved without a draft for a human to answer.
- **Prompt injection:** the customer's text is passed between markers and the system prompt says to ignore instructions in it; the output is a draft that a human approves, the intent is validated against the fixed list, and the brand-rule check runs on the draft again before sending.
- **LLM failure never loses a lead:** the LLM node continues on error; the lead is saved with an empty draft and a CHECK flag.
- **Duplicate webhook deliveries** (Meta retries) are dropped by message ID. Several messages from one contact in one delivery become one row.
- **One row per contact** (`appendOrUpdate` on `lead_id`). `first_contact_at` and the manual columns (`demo_booked`, `pilot_paid`, `notes`) are never overwritten: n8n's Sheets update skips columns missing from the item (checked in n8n-nodes-base 2.46.6 source).
- **PDPA data minimisation:** both workflows set `saveDataSuccessExecution: none`, so successful runs do not store message texts and numbers in n8n's execution log (errors are still kept for debugging).
- **Unsure, noted:** n8n's Facebook Trigger editor list does not offer `messages`/`messaging_postbacks`/`messaging_referrals` for the Page object. The node sends the field list to Meta unchanged (checked in the 2.46.6 source), so they are set in the JSON with a note on the node. The Page must also be subscribed to the app (SETUP step). Instagram DMs are out of scope (would need `instagram_manage_messages`).
- **Validator finding:** n8n's WhatsApp node has a webhook (for send-and-wait), so it needs a `webhookId` like n8n's own exports; added.
- **Runtime-tested in n8n 2.46.6:** new WhatsApp lead, duplicate delivery, STOP, Messenger with a mock LLM (echo ignored, prompt checked), LLM outage; reply sender dry run (window, do-not-contact, banned claim), live WhatsApp + Messenger (mock Graph API, request body checked) with opt-out scrubbing, and a WhatsApp API error.

### Part 5 — Workflow 4, weekly report
- **Monday 08:00 Malaysia time**, covering the 7 days before the run plus all-time totals, per pitch variant (the three pitches + "unknown" for leads without a code).
- **Counts:** posts published (`posted` only; dry runs do not count), leads (rows with a real message; "opened the chat but never wrote" is not a lead), leads who wanted a demo (intent), **demos booked** and **pilots paid** (manual columns: `yes`, `paid`, `booked`, a tick or a date count; `no`, `0`, `-`, `cancelled` do not). Also a "waiting for you" list: drafts and replies to approve, blocked/error/needs-image posts, closed reply windows.
- **Delivery:** email (n8n "Send Email" node, SMTP credential placeholder) and/or Telegram (bot credential placeholder), chosen by `REPORT_CHANNEL`. SMTP was preferred over the Gmail node because it works with any mailbox (Gmail via an app password included) and needs no extra Google OAuth scope. Missing settings stop the run with a message naming the config key.
- **Validator finding:** n8n's Send Email and Telegram nodes also have send-and-wait webhooks, so they carry a `webhookId` like the WhatsApp node.

### Part 6 — Setup guide, test plan, review
- **SETUP.md is written for a first-time n8n user** and keeps the safe order: sheet → hosted brand files → import → sheet ID → credentials → fake-data tests → Meta → go live. Meta's App Review and permission rules could not be verified from here; the guide says so and points to the App Dashboard.
- **Fake-data tests use the fictional WhatsApp number `60100000001`** in the config tab. With a real number configured, test posts containing the fictional number are (correctly) blocked by rule B9, and leftover test rows can never be published after go-live.
- **Delete unused channel nodes** (for example Telegram or the Messenger Trigger) instead of leaving placeholder credentials, because n8n refuses to start a workflow with an unusable credential anywhere in it (found in the runtime test).
- **TEST-PLAN.md has four layers:** automated (unit, validator for n8n 2.46.6 and 1.123.92, runtime test in a real n8n: 19 scenarios), manual fake-data tests in the user's n8n, live smoke tests with the owner's own phone and accounts only, and brand-rule spot checks. Known gaps are listed at the end.
- **Review was done inline, not with subagents.** The session's tool policy says not to start subagents unless the user asks, so the code-review and security checklists in `.claude/rules/common/` were applied directly. Found and fixed: approved posts were ordered by comparing `scheduled_for` as text, which misorders day-first dates typed into the sheet (now sorted by parsed time, with a test). Security checklist: no secrets (placeholders only; scan in the validator); inputs validated (config keys, URLs, image links, intents, phone numbers); no SQL; Sheets writes use RAW so inbound text such as `=IMPORTXML(...)` cannot run as a formula; the report's HTML escapes values; webhooks are signature-checked by n8n (the Messenger App Secret must be filled, SETUP says why); prompt injection is contained (markers, fixed intent list, human approval, re-check); rate limits: one post per run, at most 10 replies per run, message length capped at 1,000 characters. **Not added:** a cap on LLM calls per inbound burst, because each signed webhook carries few messages and replies need approval anyway. Long validator functions (over 50 lines) were left as is: they are linear lists of checks in a dev script.
- **The app is untouched**: only `README.md` (links) and `package.json` (`agent:*` scripts, renamed from `marketing:*` when merging `marketing-kit`) changed outside `marketing-agent/`. App lint, typecheck and its unit tests still pass (233 after merging the latest `claude/trusting-fermat-jhu3dd` commit into this branch to resolve a conflict in this file).

## Marketing kit (branch `marketing-kit`)

Made unattended; each decision logged here instead of asking.

- **Scope and guardrails in one brief.** `marketing/BRIEF.md` is the single source of facts, approved demo figures and banned claims for the AI marketing agent. `marketing/scripts/check-copy.mjs` (`npm run marketing:check`) fails on fraud/AI/guarantee/savings claims, on "replaces an accountant"/"tax advice" without a negation, and on demo figures shown without a demo-data label in the same paragraph, CSV row or page. It is a safety net; all copy was also read by hand.
- **Landing page is plain static HTML/CSS/JS** in `marketing/landing/`, not part of the Vite app, so it can be hosted alone and changed without touching the app. No framework, no build step, system fonts, and a CSP that allows only same-folder resources (no trackers can load).
- **Both languages and all three hero variants live in the HTML** and are shown or hidden with CSS from `data-lang`/`data-v` set by a 90-line script. There's no `innerHTML`, and it works without JavaScript (pitch A, English). Unknown `v`/`lang` values fall back to defaults; `src` is whitelisted to `[a-z0-9_-]{1,20}`.
- **Attribution without trackers:** the WhatsApp prefilled message carries a ref code `<pitch>-<source>` (e.g. `B-fbad`) taken from the URL. The person replying logs it in the tracking sheet. This is enough for a RM500 test and keeps the "no trackers" promise.
- **Placeholders:** WhatsApp number `60000000000` (not a valid Malaysian mobile, so it can't reach a real person by accident), Google Form `https://forms.gle/REPLACE_WITH_YOUR_FORM_ID`, accountant `[ACCOUNTANT NAME]` with a text avatar. The accountant's real name or photo goes in only with their consent.
- **No testimonials or social proof**, because we have none. The page says plainly that we can't promise findings or savings, and that a real shop may show more, fewer or none of the demo findings.
- **"Starting with a small number of shops"** is used instead of a hard number of pilot slots, because the sales kit's "2 pilots" target may grow with ads and fake scarcity is banned.
- **Screenshots are fresh captures** of the app on demo data (`marketing/scripts/capture-assets.mjs`), cropped per pitch and captured in both EN and 中文 so the page language matches the screenshots. Hero crops use a narrow 560 px viewport so the text stays legible when scaled down on phones. WebP, about 0.8 MB in total.
- **Region:** copy says "Penang" because the accountant is there and the ad test targets Penang. The FAQ doesn't promise service elsewhere.
- **Videos: one language per file** (EN UI + EN captions, 中文 UI + 中文 captions) rather than two caption lines on one video, because two stacked lines are hard to read on a phone and Xiaohongshu needs Chinese-only. So there are 8 MP4s: 60 s full ×2 and three 20 s clips ×2.
- **Full video is 16:9 (1920×1080) and clips are 9:16 (1080×1920)**, recorded on a phone-sized viewport, because the clips are for Reels/Stories/XHS and the full video is for the landing page, the feed and WhatsApp.
- **Frames come from Chromium's CDP screencast** (JPEG q92 at full device pixel ratio) through Playwright, not Playwright's built-in recorder, whose fixed low bitrate blurs small table text. ffmpeg turns the variable-rate frames into constant 30 fps H.264 `-preset veryfast -crf 21` with a silent AAC track (some uploaders reject video without audio).
- **Captions, cursor, demo badge and cards are page overlays**, so CJK text renders with the system fonts. They are manual popovers so they stay above the app's modal evidence dialog (browser top layer). The "Demo data · fictional shop" badge is on screen for the whole video.
- **Clips jump between pages directly; the full video clicks the real navigation**, to fit the 20 s length.

## Final review (branch `final-review`)

Made unattended; each decision logged here instead of asking.

### Part 1 — Accountant rule-review pack
- **Generated, not hand-written.** Worked examples are computed by running the real analyses on the demo data (`src/review/packExamples.ts`), so every number and row in the pack matches the app. The hand-written parts (false positives, what a rule can miss, the question for the accountant) are in `src/review/packNotes.ts`, in EN and 中文 side by side so they stay in step. A test fails if a rule has no notes or example, if a printed row differs from the demo file, or if the committed Markdown/HTML is stale.
- **Two PDFs (EN, 中文), not one bilingual PDF.** An accountant reads and annotates in one language; a bilingual page would double the length and halve the space for notes. Both are A4, one rule per page where it fits (PRF-01–03, SUP-04 and CSH-01 run onto a second page because of their tables), printed from HTML with Chromium (Playwright), using the WenQuanYi Zen Hei CJK font available here.
- **Examples chosen to teach, not to flatter.** PRF-02 uses CT-002, whose below-cost amount is partly caused by the tool's own simplification (current cost applied to the whole year after a May price rise), and the pack says so. STK-02 uses a CNY hamper (seasonal false positive); STK-05 uses bread (shelf life not considered); SUP-05's notes point at the demo's deposit payment.
- **Method rules (PRF-01, STK-01, STK-04, STK-05, CSH-01) get the same structure**, with "where the calculation is approximate" instead of "false positives" and "Change the method or wording" instead of a threshold box.
- **Row numbers are spreadsheet rows in `demo/data/*.csv`** (header = row 1), the same numbers the app shows under "Show source rows". At most 8 rows are printed per table; longer evidence (for example 744 sales lines for one product) goes to `docs/accountant-review/evidence/*.csv` with row numbers, and lists of more than 40 row numbers are not printed.
- **Rules version hash** (FNV-1a of the rules' JSON) on the cover and in every footer, so a signature applies to one version of the rules.
- **The sign-off says what it is not:** "a review of the tool's rules only … not an audit, review or other assurance engagement", so the accountant's signature cannot be presented as assurance on a shop's numbers.
- **Professional body field is generic** ("Professional body and membership no.") rather than assuming ACCA or MIA.
- **Price-controlled goods are mentioned with "may be"**: the pack says some staples "may be price-controlled" rather than naming which items are controlled today, because that list changes and could not be checked from here.

### Part 2 — Pilot onboarding guide
- **One guide per language (`sales-kit/06-pilot-onboarding.{en,zh}.md`), numbered after the agreement** because it is handed over after signing. Linked from both sales-kit READMEs (new step 6 in the suggested flow) and the main README.

Menu paths are given as "look for…" where they are guesses, and the fallback is always "send us a screenshot of the Reports menu" rather than retyping data.

### Part 3 — Messy-data hardening
- **Five fixtures in `tests/fixtures/messy/`** (four CSV, one `.xlsx` generated by a committed script), each combining several real-world problems, tested twice: through the import pipeline in `tests/unit/messy-files.test.ts` and by uploading them in the browser in `e2e/messy.spec.ts`. Before the fixes, file 5 could not be used at all (wrong header row), file 1 lost its SKU and net amount columns and counted a refund as a sale, file 3 counted refunds and voids as sales, and file 4 used the before-tax amount as the invoice total, so SST-inclusive payments would not match.
- **Merged two-row headers:** when the row above the header has at least two labels, fewer filled cells and no numbers or dates, its labels are carried across the merged cells and prefixed to any column whose own header means nothing ("Code" → "Item Code", "Net" → "Amount (RM) Net"). Columns whose own header is recognised keep it. The combined labels are used only when they map more columns than the plain header, and header detection uses them too. The mapping table shows the combined names.
- **SST:** a column holding only tax ("SST (RM)", "SST 10%", "Tax amount") is never mapped to a money field. When both before- and after-tax amounts exist, sales prefer before tax (SST collected is not the shop's revenue) and supplier invoices and payments prefer after tax (what is actually paid and matched to payments). Malay (sebelum/termasuk/tidak termasuk) and Chinese (不含/含税) wording is recognised.
- **Unit fields avoid "total" headers** (a small score penalty), so "Cost Total" is not taken as unit cost when "Cost Unit" exists.
- **Refund/void line type:** a new optional sales column (`Receipt type`, `Transaction type`, `Jenis`, 类型 …). "Refund/Return/Pulangan/退货" makes the line negative; "Void/Cancelled/Batal/作废" skips it with a warning. It is recognised when present but left out of the blank template and the demo files, so the demo data and the accountant pack are unchanged.
- **Note rows** with a single filled cell ("Printed by…", "Page 2 of 3") are skipped quietly: no record type can be valid with one cell, and reporting them as errors was noise. Total rows also recognise "Jumlah Keseluruhan", "Jumlah Kecil", 總計/合計 and "Total (RM)".
- **Date order is explained, not silently guessed:** a warning when every date in a column could be read either way (we read day-first, as usual in Malaysia), and another when a column mixes day-first and month-first dates. There is no manual override yet; that is listed in `docs/FINAL_REVIEW.md`.
- **Bug fixed:** the `zeroCost` and `negativePrice` warnings had no message text, so the Start page showed the raw keys `issues.zeroCost` / `issues.negativePrice`. Issue codes are now a runtime list (`ISSUE_CODES`), and a test checks that every code and every column name has text in EN, 中文 and BM.
- **Three existing tests used ambiguous dates** (`01/02/2026`) incidentally and now got the new date-order warning. Their dates were changed to unambiguous ones (`15/02/2026`) instead of weakening the warning.

## QA review fixes (13 Nov 2026)

An external QA review (ChatGPT/Codex, pinned at `2763134`) reported 13 confirmed defects and one suspected one. Each was reproduced with its reproduction kit first; the kit's probes, which asserted the faulty behaviour, became regression tests asserting the fixed behaviour (`tests/unit/qa-review.test.ts`, `e2e/qa-review.spec.ts`). No features or marketing materials were changed.

- **B01 — reviews are bound to evidence, not to a file name.** The review key now covers each file's exact bytes (SHA-256), its column mapping and its day/month order, instead of name + layout + row count. Each saved decision also stores a fingerprint of the finding (rule, subject, values, amount, evidence rows); a decision only shows on a finding with the same fingerprint, so a changed amount or changed rows starts unreviewed. Consequences: (1) reviews saved by earlier versions have no fingerprint and are not applied — they must be redone once; (2) changing a threshold that changes a finding's values (e.g. dead-stock days appear in STK-02's message) also clears that finding's review, on purpose; a threshold change that leaves a finding identical keeps it.
- **B02 — coverage is shown where the numbers are read.** Page 1 of the report and the health check now say which rows were left out, how much sales revenue has no cost, and that there is no payments file. With no readable sales or products the report shows why instead of key numbers (an all-zero report looked clean).
- **B05 — changed documented assumption (CSH-01).** Previously "Weeks run Monday to Sunday" and week 1 started on the Monday on or before the last sales date, so for a file ending mid-week, sales and costs already in the file were forecast again on top of today's cash. Now the cash-in-bank figure is taken as at the end of the last sales date (the label says the date) and week 1 starts the next day; weeks are 7 days. Files ending on a Sunday — including the demo — give exactly the same result as before. The rule text is updated in EN, 中文 and BM and the accountant pack regenerated (rules version changed). `sales-kit/DEMO_SCRIPT*.md` still quotes the old label "Cash in bank today (RM)"; left unchanged because this pass does not edit sales/marketing materials.
- **B10 — changed earlier decision.** An earlier review added "two genuinely identical lines on one invoice are not a duplicate". That left a one-line invoice keyed in twice on the same date silently doubled. Now, when every line on the date is repeated the same number of times but there are too few lines to be sure (the existing ≥4 lines / ≥2 distinct lines rule), the invoice is **flagged** as a possible SUP-01 duplicate for review, and its total is **left as entered** (still not halved). Only the stricter case is treated as keyed twice and counted once, as before. The accountant should confirm this trade-off when signing the rule pack.
- **B03, B04, B06, B07, B09, B11, B12, B13** are defect fixes that keep the documented rules: payment references are matched as separate tokens first ("INV001, INV001A" pays both), PRF-02 applies to free/100%-discounted sales of a costed product (PRF-03 still needs revenue), the duplicates headline counts each group of same-amount invoices once per extra copy, STK-03 has message text, a record called "Total" with two identity fields is kept (footers still skipped), the slow-stock headline uses the current dead-stock days, chart labels show real negative amounts, and the n8n scripts resolve Windows paths with `fileURLToPath`.
- **B14 (possible double send by two concurrent n8n runs) stays "suspected":** it needs a live n8n instance with two overlapping runs to reproduce, which this environment does not have. Keep the agent in dry-run until it is tested.
